# Album Feature — Implementation Plan

## Context

The app ("Deposito Seguro") currently organizes everything under one concept: a `FolderMetadata` record, which is either a root-level "Vault" (`parentId` undefined) or a nested "Subfolder" (`parentId` set). Files belong to exactly one folder via a single FK (`FileMetadata.folderId`) — there is no many-to-many membership model anywhere in the app.

The user wants a Google-Photos-style **Album** concept layered on top: a new kind of root-level container that only ever holds photos/videos, has no subfolders, and is reachable from Dashboard/Favorites/Search alongside — but visually separate from — regular vaults/folders. Given the existing architecture (single-FK files, no join tables, entirely local AsyncStorage + filesystem storage, no backend), the pragmatic and consistent implementation is to model an Album as a **discriminated variant of `FolderMetadata`** (`type: 'folder' | 'album'`) rather than building a parallel many-to-many system — this reuses the entire existing persistence, encryption, favorite, clipboard, and menu-action machinery for free, and matches how the user described the creation flow ("new vault modal... either an album or a root folder").

Beyond the base feature, a self-review pass surfaced two things closer to *existing bugs* than optional polish — video tiles currently render as broken images (no video thumbnailing exists anywhere in the app) and the whole file/folder grid is unvirtualized (fine at today's typical folder sizes, but an album is explicitly meant to hold many photos) — both are folded in as required, not optional. Two further "make it actually feel like Google Photos" improvements (date-grouped grid, album cover thumbnails) and one UX convenience ("Add to Album" from a file's menu) are included per follow-up discussion with the user.

Confirmed decisions (approved by user):
- **Data model**: Album = root-only `FolderMetadata` with `type: 'album'`. No migration needed — old data has no `type` field, and `undefined !== 'album'` naturally reads as a regular folder everywhere.
- **Code reuse**: Extract the Folder screen's ~1176 lines of shared grid/selection/clipboard/viewer/access-key logic into one variant-aware component, rather than forking two diverging screens.
- **Adding media to an album**: both a fresh media-picker import AND paste-from-clipboard of existing vault photos/videos (non-media pastes rejected), plus a direct "Add to Album…" shortcut (see §7).
- **Feature parity**: Albums get full parity with folders (access-key lock, favorite, rename, delete/shred, export), minus subfolders and minus "Move" (an album can never have a parent, so there's no valid destination — enforced in both directions, see §3).
- **Real thumbnails + virtualized grid**: required, not optional (§1a, §2a) — the app currently has no video-thumbnail generation at all (a pre-existing bug this feature would otherwise inherit and amplify) and no grid virtualization (fine today, not at album scale).
- **Date-grouped album grid + album cover thumbnails**: included (§2b, §3/§4 cover-thumbnail subsections) as the two highest-leverage "actually looks like Google Photos" improvements.
- **"Add to Album" quick action**: included (§7) as a cheap UX win on top of infrastructure the rest of the plan already builds.

- **`copyFileToFolder`** (~line 1294) — **this, not `pasteFromClipboard`, is the right chokepoint for the album-media-only guard**: it's the single lowest-level primitive already shared by paste-copy, duplicate, *and* the new "Add to Album" action (§7), confirmed by reading its call sites (`pasteFromClipboard`'s copy-mode, `duplicateFile`, `duplicateFolder`'s recursive copy all route through it). Add the same `isAlbumFolder(targetFolder) && !isMediaMimeType(sourceFile.mimeType)` check as `importFile`'s, throwing `AlbumMediaOnlyError`, right after resolving the target folder.
- **`pasteFromClipboard`** (~line 1104): right after resolving `srcFolders`/`srcFiles`, add **two** pre-flight guards — a nicer whole-batch UX layer *on top of* `copyFileToFolder`'s own per-call guard above, mirroring the codebase's existing dual-layer pattern for storage limits (`assertBatchWithinStorageLimit` pre-flight + `assertWithinStorageLimit` inside each individual op — confirmed by reading both):
  1. **Target-is-an-album guard**: if the paste target is an album, reject the whole paste (matching this function's existing `Alert.alert` + early-`return { pastedFiles: 0, pastedFolders: 0 }` pattern) if `clipboard.folderIds.length > 0` ("Albums can only contain photos and videos — folders can't be pasted here") or if any pasted file's mimeType isn't media (`"<name>" can't be added to an album — only photos and videos are allowed`).
  2. **Pasted-item-is-an-album guard** (catches the reverse case, easy to miss): if `targetFolderId` is truthy (i.e. the destination is *some* folder, not the vault root) and any folder in `clipboard.folderIds` has `type === 'album'`, reject the paste ("`"<name>"` is an album and can't be nested inside another folder") — regardless of whether the destination itself is a plain folder or another album, since both cases would give the album a `parentId`. Without this, a user could select an album via some future UI addition, paste it into a regular folder, and produce a nested album — silently breaking the "albums are always root" invariant that `dashboard.tsx`'s `rootFolders`/`subFolders` split, `useFileSystemQuery`, and `vaultSections.ts`'s `splitAlbums` (§4) all assume holds unconditionally. Pasting a copied album to the **root** (`targetFolderId` falsy) must stay allowed. **Reachability note (corrected — self-review pass 3):** with the v1 scope decision in §3 — **now applied app-wide, to Dashboard *and* Favorites *and* Search, not just Dashboard** (see §3's widened "no bulk-select on albums" bullet and §4's matching `renderFolderList`/`renderSelectionToolbar` fixes) — there is no UI path that can put an album into `clipboard.folderIds`. This was *not* true of the plan's earlier draft: before this correction, Favorites' and Search's shared, per-item long-press selection (already wired identically to dashboard's, confirmed by reading `renderFolderList`) would have let a user long-press-select a favorited/matched album and bulk-copy it into the clipboard via those screens' existing `handleBulkCopy`, reaching exactly this guard through real, ordinary UI — not a hypothetical. With the §3/§4 fixes applied, this guard goes back to being genuine defense-in-depth for a future UI addition (e.g. a later per-album "Duplicate"-via-clipboard shortcut), not something exercisable through today's UI. Keep it anyway.
- **`moveFolder`/`moveFileToFolder`**: guarded indirectly — see the "Move" fix in §3 (albums excluded from every move-destination list, and "Move" omitted from an album's own menu in §2).
- Deliberately unchanged otherwise: `duplicateFolder`, `renameFolder`, `deleteFolder`, `shredFolder`, `toggleFolderFavorite`, `assignFolderAccessKey`/`removeFolderAccessKey`, `copyToClipboard`/`cutToClipboard`, `exportFolderFiles` — all already generic over any `FolderMetadata` and need no changes. (`duplicateFolder`'s internal copy already spreads the source record, so `type` carries through automatically — duplicating an album correctly yields another root-level album.)
- **Confirmed safe, no change needed**: `copyFileToFolder`'s existing icon-copy logic (~lines 1326-1349) is already generic over any `iconPath`, not `.apk`-specific — it copies `sourceFile.iconPath` to a new sandbox path and re-derives `iconEncrypted` whenever `iconPath` is set, with no mimeType branch. Once §1a's `importFile` starts populating `iconPath` for media files, duplicating a file or pasting/copying it into an album automatically carries its thumbnail forward with zero changes to `copyFileToFolder` required.

**[src/services/backupService.ts](src/services/backupService.ts)** — the folder export step (~line 184) manually allowlists fields (`id, name, color, icon, ...`) rather than spreading — add `type: f.type` to that allowlist, or a freshly-created album silently reverts to a plain folder on backup/restore. The restore path writes the manifest straight through, so no restore-side change is needed once export carries the field.

## 1a. Real thumbnail generation (required — fixes a pre-existing bug, not album-only)

**Confirmed by reading the current code**: [src/hooks/useFileThumbnailUri.ts](src/hooks/useFileThumbnailUri.ts) unconditionally returns `file.localPath` for *any* image or video, and the grid tile feeds that straight into `<Image source={{uri}}>` (`GridTile.tsx`). Two consequences, already true today, before this feature exists:
1. **Every video tile in the app renders broken** — an `<Image>` component cannot decode video file bytes into a frame. There is no video-thumbnail generation anywhere in the codebase (confirmed: `expo-video` is installed and used only by the video *viewer*, never for a grid preview).
2. **An encrypted image's tile also renders broken** — `localPath` for an encrypted file points at ciphertext, and the hook's own comment already documents this as a known, deliberately out-of-scope gap ("a file encrypted itself just renders as a broken image... that gap is out of scope for this hook").

Both matter more once albums exist (a screen whose entire purpose is a dense photo/video grid), and both are fixable with one coherent change that also improves grid performance (a full-resolution photo is often several MB; decoding dozens of them for 100px tiles is wasteful).

**Reuse, don't add new fields**: `FileMetadata` already has `iconPath`/`iconEncrypted` — "cache path to a small preview image extracted at import time... independent of `localPath`", today populated only for `.apk` launcher icons. Extend the *same* mechanism to images/videos instead of adding parallel fields:

- **New dependencies** (not currently installed — confirmed via `package.json`): `expo-image-manipulator` (downscale a photo to a small JPEG) and `expo-video-thumbnails` (extract one frame from a video). **Before adding either, check their exact SDK 57 API shape** at `https://docs.expo.dev/versions/v57.0.0/sdk/imagemanipulator/` and `https://docs.expo.dev/versions/v57.0.0/sdk/video-thumbnails/`, per AGENTS.md's "Expo has changed" instruction — same rationale as the `expo-image-picker` doc-check in §2.
- **`vaultStore.ts`'s `importFile`** — confirmed exact insertion point by reading the function (lines 452-515): the sequence today is `copyToSandbox` → `remuxVideoIfPossible` (video-only remux) → `.apk` icon extraction (`extractApkIcon`, gated on `isApk`) → the conditional-encryption block (`if (encrypt && encryptionKeyId)`, which also encrypts whatever `iconPath` holds and sets `iconEncrypted: true`). Insert the media-thumbnail step in that **same slot** the `.apk` extraction already occupies — right after `remuxVideoIfPossible`, right before the encryption block — just gated on `isMedia` (image/video mimeType) instead of `isApk`: generate a small thumbnail (image: resize to e.g. 300px longest edge; video: grab the frame at `time: 0`), write it into the sandbox, and set it as `iconPath` exactly like the `.apk` path already does. Because this lands in the same slot, the existing encryption block needs **no changes at all** — it already encrypts whatever `iconPath` is set at that point and sets `iconEncrypted: true`, with no awareness of *why* `iconPath` was set, mirroring the `.apk` icon flow's own S-12 remediation. If thumbnail generation fails for any reason (corrupt file, unsupported format), fall back gracefully — leave `iconPath` unset and let the read side fall back to `localPath` (next bullet), rather than failing the whole import.
- **`useFileThumbnailUri.ts`** — remove the hard `!isMedia` exclusion from `needsIconDecrypt`'s condition, and change the resolution order to: **prefer `iconPath` whenever it's set** (decrypting via the existing `needsIconDecrypt`/`decryptedIconUri` machinery when `iconEncrypted`, otherwise read directly), **falling back to today's behavior** (`file.localPath` for media, `undefined` otherwise) only when `iconPath` is unset — i.e. for files imported before this change ships. This is fully backward compatible: no migration, older files just keep rendering exactly as they do today until re-imported.
- **Video duration badge**: out of scope for this pass — `expo-video-thumbnails` doesn't return duration, and probing it separately at import time is more machinery than this warrants right now. Note as a natural follow-up once real video thumbnails exist, not a blocker.
- **Scope note**: this applies to *every* image/video import app-wide (folder or album), since it's the same `importFile`/`copyFileToFolder` code path either way — branching it album-only would need extra, pointless conditionals for no benefit, and folder screens showing photos benefit from the same fix.

## 2a. Grid virtualization (required — same reasoning as §1a: correctness at album scale, not style)

**Confirmed by reading the current code**: `folder/[id].tsx` renders its entire subfolder/file lists inside one `ScrollView`, with the "grid" being a plain `flexWrap: 'wrap'` `View` of `GridTile`s — every item is mounted at once, nothing is windowed. Acceptable for a typical mixed-file vault folder; not acceptable for a screen explicitly meant to hold a large photo/video library, where mounting hundreds of `<Image>` views at once is a real jank/memory risk (compounded by real thumbnails now being generated per §1a, which helps, but doesn't eliminate the problem — a hundred small images is still a hundred mounted components plus list/measurement overhead).

**Design**: replace the `ScrollView` + wrapped-`View` grid with a single virtualized `SectionList`, used by *both* variants (keeps one rendering path in the shared component rather than branching the container itself by variant):
- New helper `chunkIntoRows<T>(items: T[], columns: number): T[][]` (e.g. `src/utils/gridRows.ts`) — splits a flat array into row-arrays of `columns` items each (last row may be shorter). In list mode (`viewMode === 'list'`), `columns` is already `1` via the existing `gridColumns(viewMode)` call, so this naturally degenerates to one item per row with no special-casing.
- `folder` variant sections: `[{ title: 'SUBFOLDERS', data: chunkIntoRows(displayedFolders, columns) }, { title: 'FILES', data: chunkIntoRows(displayedFiles, columns) }]` (each omitted/empty per the existing search/empty logic).
- `album` variant sections: date-grouped — see §2b.
- `renderItem({ item: row })` renders one `flexDirection: 'row'` of `GridTile`/`ListRow`s for that row — the exact same per-item rendering logic that exists today, just invoked once per row instead of via `.map()` inside a manually wrapped `View`.
- `ListHeaderComponent`: everything currently above the grid (search bar, stats `Card`, `ClipboardBar`, the Add/Create/Select action row).
- `ListEmptyComponent`: the existing `EmptyState`s (no-search-results / folder-empty), gated the same way as today.
- **Accepted trade-off**: today's `CollapsibleSection` gives each section a Reanimated expand/collapse animation; approximating "collapsed" as `data: []` on a `SectionList` section keeps the header visible with an empty body (same end state) but loses that animation. Not reimplementing the animation inside a `SectionList` for v1 — flag this as a known, deliberate minor UX regression versus today's folder screen, not an oversight.
- **Sequencing note**: this is a large-enough architecture change that it should land as its own step *after* the plain-extraction Phase 2 is verified, and *before* the album-specific Phase 3 (which needs it for date grouping anyway) — see Execution Phases.

## 2b. Date-grouped album grid (bigger call — included per follow-up discussion)

Album-variant-only, and the one addition that most makes the screen actually *feel* like Google Photos rather than "a folder screen that only allows photos." Built directly on §2a's `SectionList`:
- New helper `groupFilesByDate(files: FileMetadata[]): { label: string; files: FileMetadata[] }[]` (e.g. `src/utils/dateGroups.ts`) — sorts newest-first by `importedAt` and buckets into "Today" / "Yesterday" / then month-level labels ("March 2025") for everything older. Confirmed no existing bucketing utility fits: `trash.tsx`'s `formatDeletedAt` (the only candidate worth checking) is a local, non-exported, single-value relative-time formatter, not a grouping function — write `groupFilesByDate` and its label logic fresh in the new `src/utils/dateGroups.ts`, no reuse search needed.
- **Known, accepted limitation**: grouping is by `importedAt` (when the file was added to the vault), not photo-taken date — this app doesn't currently extract EXIF capture dates from images. Real Google Photos groups by capture date. Matching that exactly would need an EXIF-reading step added to the import pipeline, which is out of scope for this pass; flagged here so it isn't mistaken for a bug later.
- Each group becomes one `SectionList` section (`title: group.label, data: chunkIntoRows(group.files, columns)`), replacing the folder variant's "SUBFOLDERS"/"FILES" sections entirely for `variant === 'album'`.
