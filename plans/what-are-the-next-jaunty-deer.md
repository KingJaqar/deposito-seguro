## Context

The 2026-08-28 re-audit (`plans/deposito-seguro-audit-report-2026-08-28.md`) scored the app **78/100**, up from 51/100. Every remaining point loss traces to a specific, already-identified finding — there is no unknown work here, just a prioritized list to close out. This plan translates §17/§18/§19 of that report into an executable sequence, verified against current code (all findings below re-confirmed against HEAD today, with exact current line numbers — a few had drifted a couple of lines from the report's own citations).

**Important caveat on "100/100":** two of the eight scorecard categories (Functionality, Reliability, Testing) are partly held down by things code changes alone can't close — the report is explicit that real-device runtime behavior (does the app actually launch/auth/import/preview end-to-end) is "Not verifiable" by static analysis + `jest`, independent of how many findings get fixed. This plan closes every *code-level* gap the scorecard cites — including two the first pass of this plan missed (see items 4 and 9 below) — which should realistically move the score from 78 into the low-to-mid 90s. The last mile to a literal 100/100 additionally needs an actual device/emulator pass and a deliberate production EAS profile, flagged separately at the end.

### Post-Phase-A audit (2026-08-29): item 2 (I-22) had a residual multi-file batch gap

A deep read of the merged Phase A code (prompted by a request to re-verify the plan, not part of the original execution pass) found that item 2's fix, while landed and tested, did not actually close I-22 for the multi-file case. **Resolved 2026-08-29** — fixed in the same session, folded into Phase A rather than opened as a new item, since it's a direct completion gap in an already-"done" item, not new scope:

- **The gap:** `copyFileToFolder`'s `assertWithinStorageLimit` check reads `get().files` — the last *committed* store state — every time it's called. `duplicateFolder` and `pasteFromClipboard`'s copy mode both call `copyFileToFolder` once per file across a whole batch (a folder's full subtree, or a multi-select paste) but only `commitVaultState` once, at the very end. So no file's check in the batch ever sees the bytes the *other* files in the same batch are about to add — each only compares itself against the stale pre-batch total. A folder of 10×200MB files against a 1GB limit passed every individual check (each saw 0 committed usage) and would have landed at 2GB actual usage: the exact bypass item 2 was written to close, just one level up (single-file copy was correctly enforced; multi-file batches were not).
- **The fix:** added `assertBatchWithinStorageLimit` (`vaultStore.ts`), which sums the *entire* batch's projected bytes and checks once, up front, before any byte is copied. `duplicateFolder` and `pasteFromClipboard`'s copy branch each now walk their own file set once to build that batch total, call it before starting, then pass a new `copyFileToFolder(..., { skipLimitCheck: true })` option through every call in that batch so the (now-redundant, and wrong for this case) per-call check doesn't also run. Single-item paths (`duplicateFile`, single-file paste, `importFile`) are unaffected — one file per commit was always correct.
- **Belt-and-suspenders:** also added cleanup in both functions' `catch` blocks for any physical file already copied to disk before a later failure in the same batch (`removeFilePayload` on the batch's `newFiles` so far) — currently defensive rather than load-bearing, since `copyFileToFolder`'s own physical-copy failures are swallowed-and-logged internally rather than rethrown, so today the only realistic pre-commit throw is the new upfront batch check itself (which fires before any copy starts, leaving nothing to clean up). Worth keeping as insurance against that swallow-and-log contract changing later, or a novel throw appearing anywhere else in the loop.
- **Tests:** 3 new cases in `vaultStore.test.ts` ("I-22 follow-up" describe block) — `duplicateFolder` and `pasteFromClipboard` each blocking a multi-file batch that overflows only in aggregate (each file fits individually — this is exactly what the old per-file check missed), plus a test confirming zero physical copies happen when the batch check fails (checked before copying starts, not cleaned up after).
- **Verification:** `npx tsc --noEmit` clean, `npx expo lint` unchanged at 5 errors / 16 warnings, `npx jest --ci` 79/79 passing (76 + 3 new).

### Post-Phase-C audit (2026-08-29): item 2's family had a second, distinct accounting gap — committed encrypted files undercounted their own footprint

Prompted by a request to re-verify the whole plan against code before starting Phase D. The batch-check gap above (multi-file undercount within one operation) was confirmed fixed and correct on re-read. A different, longer-lived gap in the same two functions (plus `getVaultUsageBytes`) was found by tracing where `FileMetadata.size` is actually set and never re-derived: **Resolved 2026-08-29**, fixed the same session, folded in here rather than opened as a new item, for the same reason as the batch-check gap — a completion gap in an already-"done" item, not new scope.

- **The gap:** `size` is set once in `importFile` from the picker's `asset.size` (the original, pre-encryption byte count) and never updated afterward — not by encryption, not by re-keying (`encryptFileWithKey`). `projectedFileBytes` pads by ~1.4x for AES-CBC+HMAC's base64 + IV/MAC overhead, per its own comment, "so the limit isn't quietly exceeded by ciphertext growth" — but that padding was only ever applied to the *incoming* file being checked in `assertWithinStorageLimit`/`assertBatchWithinStorageLimit`. Both functions summed already-committed files' raw `f.size` for "used bytes," which silently drops ~40% of every encrypted file's real disk footprint back out of the running total the moment it's committed. `getVaultUsageBytes()` (the number shown against the limit in `settings/storage.tsx`'s progress bar) had the identical undercount. In a vault whose purpose is storing encrypted files, this compounds with every encrypted import: real disk usage can run meaningfully past the configured limit even though every individual check passes, and the progress bar itself underreports actual usage — a user could see comfortable headroom and then hit an unexplained rejection, or in the worst case exhaust real device storage while the app still reports being under its own cap.
- **The fix:** added a `committedFileBytes(f)` helper (`vaultStore.ts`, next to `projectedFileBytes`) that applies the same projection to an already-committed file, keyed on its own `isEncrypted` flag. `assertWithinStorageLimit`, `assertBatchWithinStorageLimit`, and `getVaultUsageBytes` all now sum `committedFileBytes` instead of raw `f.size` for "used." `f.size` itself is untouched — it's still the honest original document size wherever it's shown as a file's size in the UI; only the three quota-accounting call sites changed, so "used" and "about to use" are computed on the same basis everywhere they're compared, including the progress bar against the limit it's drawn next to.
- **Tests:** 3 new cases in `vaultStore.test.ts` ("Storage-limit accounting" describe block) — `getVaultUsageBytes` reporting the projected total for a mixed encrypted/unencrypted vault; a second import rejected only because an earlier encrypted file's *real* footprint (not its raw size) crosses the limit; and `duplicateFile` blocked by the same effect via the copy path. All three fail against the old `sum + (f.size || 0)` accounting and pass against `committedFileBytes`.
- **Verification:** `npx tsc --noEmit` clean, `npx expo lint` unchanged at 0 errors / 16 warnings, `npx jest --ci` 87/87 passing (84 + 3 new).

### Independent adversarial review (2026-08-29), after Phase D: 6 new confirmed bugs found and fixed, 4 documented as new items

None of Phases A–D's own re-verification passes (above) were adversarial in the sense of actively hunting for *new* defects outside the specific line ranges each item's own fix touched — they re-checked that each item's *own* claims still held. This pass was different: an 8-angle review (line-by-line diff scan, removed-behavior audit, cross-file call-site tracing, reuse/simplification/efficiency/altitude/conventions) run across the *entire* uncommitted diff, with every candidate finding re-verified directly against source (not taken on the finder's word) before being acted on. It surfaced defects genuinely outside every prior pass's scope — not completion gaps in a specific item's own stated fix, but bugs in adjacent code the diff touched or depended on.

**Fixed the same session (folded in here, same disposition as every other post-phase gap above — a real defect closed on discovery, not filed and left open):**

1. **Video scrubber/clock permanently freezes after any seek** (`src/app/(main)/viewer/video.tsx`) — item 8's own `search.tsx`/`video.tsx` "adjust state during render" fix for the `pendingSeekTime` I-23 lint error left `pendingSeekTime` un-nulled once playback caught up to a seek target, reasoning that playback "only moves forward" so it couldn't drift back within range of a *passed* target. That reasoning never covered continuing to play *past* the target: `rawCurrentTime` keeps advancing every frame while the un-cleared `pendingSeekTime` stays fixed, so the gap exceeds the 0.5s threshold again within half a second of catching up, flipping the display back to the stale seek time for the rest of playback. Fixed by still clearing `pendingSeekTime` once caught up, synchronously in the render body (not a `useEffect`, so it doesn't trip `react-hooks/set-state-in-effect`) rather than leaving it stale.
2. **Item 4/I-12's fix only checked one folder level** (`src/store/vaultStore.ts`, `deleteFolder`) — a file with no access key of its own, sitting in an *unlocked* folder nested under a *locked* grandparent, was only ever reachable by unlocking that grandparent. Deleting the unlocked immediate parent — an entirely ordinary action that never touches the locked ancestor — erased that gate exactly as the original I-12 gap did, but the single-level `folder?.hasAccessKey` check the first fix added didn't see it (`folder` here is the unlocked immediate parent, not the locked grandparent). Fixed by walking the deleted folder's own ancestor chain (via `parentId`, cycle-guarded) for the nearest lock, not just checking the one folder being deleted.
3. **Item 9's boot sweep can race an actively-open viewer** (`src/services/storage.ts`, `sweepOrphanedPlaintextTempFiles`) — the function's own doc comment asserted no in-flight decrypt could ever race it because it "only ever runs once, at cold boot, before any viewer could possibly be mid-decrypt." That isn't actually enforced: `_layout.tsx`'s splash-hide has its own 500ms fallback timer independent of the sweep finishing (a deliberate escape hatch for a *different*, earlier bug — a hydration that hangs forever), and nothing gates screen navigation on hydration/sweep completion (`HydrationContext`'s `isReady` has zero consumers anywhere in the app). On a slow device or large vault where hydration+sweep together exceed 500ms, a file opened in that window produces the exact bare-name+".enc"-sibling pairing a genuine orphan has, mid-decrypt — the sweep could delete it out from under the open viewer. Fixed with an mtime guard: only delete a candidate whose on-disk modification time predates the sweep call by more than a few seconds of slack. A decrypt racing the sweep necessarily writes its plaintext at (or after) that same moment, so it can never look "old enough"; a true leftover from a prior session always is. Deliberately did *not* touch the splash-hide timing itself, to avoid reintroducing the hung-boot bug that escape hatch exists for.
4. **`deleteAccessKey`/`deleteEncryptionKey` misreported a persist failure as "not found"** (`src/store/settingsStore.ts`) — item 6's own rethrow-on-persist-failure change meant `commitSettingsState`'s `set()` (removing the key from `state.accessKeys` and the visible UI list) always ran *before* the throwing `persistSnapshot` await, but both functions' single outer `try/catch` collapsed that failure into the same `'not-found'` result used for "this id never existed." `access-keys.tsx` then told the user "This access key no longer exists" for a key it had just deleted from memory a moment earlier — actively misleading about whether the deletion would survive a restart. Fixed by splitting the in-use-check and the persist call into their own `try/catch`es, with persist failure now reported as a distinct `'persist-failed'` status; `access-keys.tsx` shows an accurate "may not be saved, try again" message for it. The existing test asserting the old `'not-found'` collapse (which had never checked whether the key was actually still in memory) was rewritten to assert the correct, distinct outcome; a second test confirms genuinely-nonexistent ids still short-circuit before any persist attempt.
5. **`createAccessKey`/`createEncryptionKey`'s validation-rejection path triggered a pointless persist write that could now throw** (`src/store/settingsStore.ts`, `commitSettingsState`) — a duplicate-label or 20-key-limit rejection returns `{}` from the updater (no actual state change), but `commitSettingsState` called `persistSnapshot` unconditionally regardless of what the updater returned. Once `persistSnapshot` rethrows on failure (item 6), a storage hiccup during that redundant, no-op write turned a pure validation rejection into a thrown error the caller had no reason to expect, and would have surfaced as a generic "failed to create" toast instead of the specific duplicate/limit message. Fixed by skipping the persist call when the patch is empty — a safe general rule since every real mutation's updater returns a non-empty patch.
6. **`removeFileEncryptionKey` was the one call site the S-11/item-3 audit missed** (`src/store/vaultStore.ts`) — every sibling function reached by `decryptSandboxFile`'s new throw-on-missing-key behavior (`removeFolderEncryptionKey`, `assignFileEncryptionKey`) wraps the call in its own try/catch; this one didn't. No live UI caller today (same disposition Phase A/B already found for `assignFileEncryptionKey`/`createEncryptionKey`), but it's exported on the public store interface, so a future caller with no try/catch of its own — a realistic pattern given every other key action in this codebase is fire-and-forget from the UI — would hit an unhandled promise rejection instead of a clean, logged failure. Fixed with the same try/catch pattern as its siblings.

**Tests:** 1 new case in `vaultStore.test.ts` (nested-inheritance regression, item 2 above), 2 in `settingsStore.test.ts` (persist-failed vs. genuinely-not-found, item 4 above — the existing test that asserted the old, wrong behavior was rewritten rather than left alongside a contradictory new one), 1 new case plus 3 existing sweep tests updated with `modificationTime` fixtures in `storage.test.ts` (item 3 above — the existing tests didn't register per-file `getInfoAsync` mocks at all, since the mtime check didn't exist yet when they were written).

**Verification:** `npx tsc --noEmit` clean, `npx expo lint` 0 errors / 17 warnings (17 vs. Phase D's reported 16 is not a regression from this pass — every current warning's line falls outside every file/region touched by these six fixes; likely just a more precise recount than Phase D's own, since the exact pre-Phase-D warning list was never fully captured, only its total). `npx jest --ci` 118/118 passing (115 + 3 net new test cases; one existing test rewritten in place, not counted twice).

**Documented rather than fixed (lower severity, or a design question rather than a defect) — added to the work-items list below as items 16–19:**

- `backupService.ts`'s `restoreBackup` reports success even when its `updateSetting('encryptionDefault', ...)`/`updateSetting('autoLockDuration', ...)` calls silently failed to persist (item 16).
- `copyFileToFolder`'s `skipLimitCheck` option is an unenforced convention, not a structural guarantee — a future batch caller could reintroduce the I-22 bypass by omission (item 17).
- `deleteFolder`'s inherited-access-key snapshot (fix #2 above) is indistinguishable from a key the user assigned directly to the file — no marker records which is which (item 18).
- `pasteFromClipboard`/`duplicateFolder` each walk the same folder subtree twice — once to sum bytes for the upfront batch limit check, again to actually copy (item 19).

**Noticed but not verified end-to-end — flagged for the user rather than asserted as fact:** while tracing `deleteFolder`, its folder-removal line (`state.folders.filter(f => f.id !== folderId)`, pre-existing, not touched by any phase of this plan) appears to only ever remove the single folder being deleted — never its child folders. No caller found anywhere in the UI recurses over subfolders before calling `deleteFolder` either. If that reading is right, deleting a folder that has subfolders would leave those subfolders (and every file inside them) as live, non-trashed data with a `parentId` pointing at a folder that no longer exists — neither deleted nor protected nor (depending on whether any screen lists folders independently of their parent's existence) necessarily reachable through normal navigation. This is a plausible, potentially serious gap, but it predates every phase of this plan, is architecturally larger than a completion-gap fix (a real recursive-delete-or-block-on-non-empty design decision, not a one-line patch), and was not confirmed against every folder-listing surface in the app — added as item 20 for a dedicated look rather than guessed at here.

### 4. [Major] I-12 — Fix trash-restore folder-protection inheritance (previously only disclosed, not fixed)
**File:** `src/store/vaultStore.ts`, trash/restore logic (confirmed at `restoreFileFromTrash`, ~L421-472 — `landedInFallbackFolder` return added but the underlying gap is unchanged). Currently, restoring a file whose original folder no longer exists silently drops it into an unprotected "Restored Files" fallback folder, losing whatever access-key/encryption protection the original folder provided; the only fix applied so far is surfacing `landedInFallbackFolder` as a UI warning rather than actually preserving protection. The scorecard explicitly still counts this against the Backend/data-integrity score.

**Design decision (resolved 2026-08-29, confirmed against current code before writing anything):**

Protection state is captured as a direct snapshot onto the file's own `hasAccessKey`/`accessKeyId` fields — no new type field needed. It's applied at the one place a file can actually lose its folder's protection: inside `deleteFolder` (L345-350), in the same commit that removes the folder's metadata, for every file being cascaded to trash (`f.folderId === folderId`) that doesn't already carry its own access key.

This is the single reachable gap, confirmed by reading the surrounding code rather than assumed: `assignFolderEncryptionKey`/`removeFolderEncryptionKey` (L682-712 area) already cascade real encryption onto every child file's own `isEncrypted`/`encryptionKeyId` (Finding I-9, already fixed elsewhere) — so a file is never relying on folder-only encryption; it always carries its own copy. But `assignFolderAccessKey`/`removeFolderAccessKey` (L656-680) only ever touch the folder's own fields, never cascade to files — so a file with no access key of its own, sitting in a password-locked folder, is protected purely by the "must unlock this folder to browse into it" navigation gate. That gate is exactly what deleting the folder erases. `FolderMetadata` has no `isTrash`/`deletedAt` of its own (only files get trashed; folders are removed outright), so `deleteFolder` is the *only* place folder metadata is ever discarded — both orderings (file trashed first, then its folder deleted later; or the folder deletion itself cascading the file into trash) funnel through this one function, so one hook point covers both.

Folder-level `isEncrypted`/`encryptionKeyId` inheritance needs no fix here: it's already cascaded live onto files by I-9, so there's nothing left to lose when the folder disappears.

- In `deleteFolder`, when building the cascaded-trash `files` update, for a file whose `folderId` matches and that doesn't already have its own `hasAccessKey && accessKeyId`, if the folder itself has `hasAccessKey && accessKeyId`, stamp `hasAccessKey: true, accessKeyId: folder.accessKeyId` onto the file in the same update as `isTrash: true`.
- `restoreFileFromTrash`'s existing behavior already needs no change to preserve this — `hasAccessKey`/`accessKeyId` are never cleared by the restore path, so a snapshot taken at delete-time rides along automatically. What does need updating: the return value should also report whether the restored file itself ended up protected, so the UI warning is accurate rather than blanket "unprotected" — add e.g. `filePreservedAccessKey: boolean`.
- Update `trash.tsx`'s restore-toast copy (single and bulk) to branch on that flag: when true, say the "Restored Files" folder itself is unprotected but this file is still password-locked; when false, say the file is now fully unprotected. Keep the existing warning for the "wrong folder" part — that's honest and worth keeping.
- New test coverage in `vaultStore.test.ts`: a file with no access key of its own, inside an access-key-protected folder, trashed and then the folder deleted (and the reverse ordering: folder deleted first, cascading the trash) — assert the file carries `hasAccessKey`/`accessKeyId` after `deleteFolder`, and that `restoreFileFromTrash` reports `filePreservedAccessKey: true` and the file keeps them after restore.

- **Environment note:** `npx expo run:android` (the normal one-command build+install+launch flow) fails outright — it probes any `emulator-*`-named adb target with `adb emu avd name` to resolve a display name, which only real QEMU AVDs support; this device turned out to be an x86_64 VM running under VirtualBox (confirmed via `VBoxNetNAT.exe` holding the port-forward, and `ro.product.cpu.abi=x86_64`), not a QEMU AVD, so it has no emulator console port and the probe errors before ever reaching a build. `npx expo start`'s own device auto-open logic hits the identical probe. Noting this here in case a future session hits the same "expo CLI inexplicably fails against an already-connected device" symptom — the fix is the device type, not the project config.
- **Two more environment-only fixes were needed before a build would even compile, neither related to the app's own code:**
  1. `android/local.properties` had no `sdk.dir` and `ANDROID_HOME`/`ANDROID_SDK_ROOT` are unset in this shell — added `sdk.dir` pointing at the installed SDK (`C:/Users/User/AppData/Local/Android/Sdk`).

Both fixes are local-only (the whole `android/` directory is gitignored, regenerated by `expo prebuild`), documented with comments in the files themselves for whoever hits this next.
- **Bug found and fixed — mipmap resource names (build-blocking, pre-existing, unrelated to any prior phase):** the native build failed outright with `Error: '-' is not a valid file-based resource name character` on every disguise-icon mipmap PNG. `plugins/withDisguiseIcon.js` (last touched in commit `90ef6fb`, weeks before this whole audit effort — confirmed via `git log`, not part of any phase above) copies `assets/icons/calculator-icons/calculator-icon-<theme>.png` straight into `android/app/src/main/res/mipmap-*/` under the *same hyphenated filename* — valid for a plain asset, but Android's aapt2 resource compiler rejects a hyphen in a file-based resource name outright. This is exactly the class of defect only a real native build can surface: `tsc`/`eslint`/`jest` never touch generated Android resources, so it had presumably been broken since whenever this was last touched, with nothing in any prior phase (including this session's own earlier review) able to catch it. **Fixed** in `plugins/withDisguiseIcon.js`: added a `mipmapResourceName(theme)` helper (`calculator-icon-black-orange` → `calculator_icon_black_orange`) used consistently for both the copied mipmap filenames and the `AndroidManifest.xml` activity-alias `icon` references that point at them, so the two can't drift out of sync again. Verified by a full `expo prebuild --clean` + native build succeeding afterward.
- **Structural discovery — the debug build can never reach Metro, on any device:** even after the app installed and launched, the JS bundle failed to load (`Unable to load script... Make sure you're running Metro`), despite `adb reverse tcp:8081 tcp:8081` being confirmed active and `adb shell curl http://localhost:8081/status` succeeding from the device's shell. Root cause: `app.json`'s Android `blockedPermissions` strips `INTERNET` (confirmed in the merged manifest: `<uses-permission android:name="android.permission.INTERNET" tools:node="remove"/>`) — a deliberate, correct security-hardening choice for a vault app (no code path can ever open a network socket, full stop), but as a side effect it means the *app process itself* (not the adb shell, which is unaffected) can never open a socket to fetch a bundle from Metro either, on any device, ever. This isn't fixable without weakening the security posture — the only way to actually run this app outside `jest` is a build with the JS bundle embedded into assets at build time (what a release build does). Worked around locally by setting `debuggableVariants = []` in `android/app/build.gradle` (gitignored, not committed) so the debug variant goes through the same `export:embed` bundling path a release build uses. **Worth recording as a standing fact about this project, not just a one-off workaround:** any future device-testing session should expect this and go straight to an embedded-bundle debug (or release) build rather than losing time on a live Metro connection.
- **Bug found and fixed — screenshot protection (S-9) silently never worked on a real device:** once the embedded-bundle build actually launched and the JS ran, `disguiseIcon.ts`'s `setFlagSecure` native call threw `android.view.ViewRootImpl.CalledFromWrongThreadException: Only the original thread that created a view hierarchy can touch its views` — caught and logged, not fatal, but meaning **`FLAG_SECURE` was never actually being set**, on every single invocation, despite `screenshotProtection` defaulting to `true` specifically so "a vault app should protect screenshots/recent-apps thumbnails out of the box" (S-9's own comment). Root cause: `@ReactMethod` bodies run on a background thread by default; `DisguiseIconModule.kt`'s `setFlagSecure` called `activity.window.addFlags(...)` directly from that thread, and `Window`/`ViewRootImpl` are UI-thread-only. This is a second defect only reachable via an actual on-device run — impossible to catch from `jest`'s DOM-less test environment, and impossible to catch from source review alone without knowing React Native's threading model well enough to spot it (this session's earlier 8-angle review did not catch it either, since it never executes native code). **Fixed** in `plugins/withDisguiseIcon.js`: wrapped the `Window` flag mutation in `activity.runOnUiThread { ... }`, keeping the promise resolve/reject inside that block.
