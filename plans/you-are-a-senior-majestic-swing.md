# Deposito Seguro — Full Frontend/UI Redesign Plan

## Context

Deposito Seguro is a fully local/offline encrypted-vault mobile app (Expo 57, RN 0.86.2, React 19.2, expo-router 57) — no backend, no APIs, all data in on-device storage (AsyncStorage + SecureStore + a sandboxed filesystem) with local ZIP backup/restore. The app also disguises itself as a calculator ("Calculator Spoofing") to hide its existence from a casual observer.

The current UI has accreted across many iterative passes: six theme palettes with an inconsistent token schema (a `dashboardX?`/`fabX?` namespace populated on only 2 of 6 palettes, papered over by a `colors.dashboardX ?? colors.X` fallback pattern copy-pasted **133 times** across 12 files — verified by `git grep -o "?? colors\.\|?? dash\." 0f05a73 -- src | wc -l`), 19 hand-rolled components spanning **~24 near-duplicate modal call sites** (8 named components plus **16 inline `<Modal>` blocks across 6 screen files** — dashboard 2, favorites 3, folder 4, search 2, settings/index 4, trash 1), a `VaultHeader` with inconsistent safe-area ownership (a real double-top-padding bug on its **5 host files**, and **iOS-only** — three of those hosts use React Native's own `SafeAreaView`, which is a no-op on Android; see §5), and several real bugs (a storage progress bar hardcoded for dark backgrounds that's invisible in light theme, a central tab-bar button whose color never follows the active theme/disguise skin). This plan is a **total teardown of that presentation layer, not a restyle of it** — every color, every component file, every screen layout is deleted and rebuilt from a new design system; nothing visual survives just because it's already there. The one thing held fixed is the engine under the hood: every stored fact, workflow, validation rule, and line of business/security logic stays byte-for-byte identical, and the rebuild is sequenced in phases purely so that engine can be verified untouched at each step — the phasing is an engineering safety net, not an excuse to keep old UI code around longer than necessary. Old files superseded by a new primitive are deleted in the same phase that replaces them, not kept as compatibility shims.

The working tree currently has an uncommitted, unrelated UI polish pass in progress (a `TabRootHeader` header-consolidation refactor + a `wrapAtLength` dedupe util, ~34 modified files). Per the user's explicit choice, this uncommitted work is discarded — implementation starts from a clean checkout of the last commit (`0f05a73`), not layered on top of it.

> **Critical consequence of that reset — read before Phase 0.** `src/components/TabRootHeader.tsx` and `src/utils/wrapAtLength.ts` are **untracked**, i.e. they exist *only* in the work being discarded. At `0f05a73` neither file exists, and **no tab-root screen uses a shared header** — all five hand-roll an inline header block. Therefore, everywhere this plan refers to `TabRootHeader` or `wrapAtLength`, treat them as **net-new files to be authored**, never as existing baseline to restyle or "keep as-is". (Whether `TabRootHeader` is authored fresh or salvaged from the stash is an **open decision flagged in §7 Phase 3, step 1** — resolve it before Phase 3 begins; this plan assumes "authored fresh".) In particular, the claim that `VaultHeader` should adopt "the pattern `TabRootHeader` already uses" is void — that pattern must be written from scratch (§5). Additionally, **this plan file itself (`plans/you-are-a-senior-majestic-swing.md`) is untracked**, so a blanket `git clean -fd` during Phase 0 would delete it. Phase 0 must use the exact, exclusion-aware command sequence given in §7.

Research for this plan came from three parallel codebase audits (screens/navigation, components/design-system, business-logic/state layers) plus a dedicated design-system specification pass. Key finding that shapes the whole plan: **all business logic is cleanly separated except in `src/utils/getFileType.tsx`** (file-classification logic fused to hardcoded icon JSX) **and `src/components/AccessKey*.tsx` / `FolderPicker.tsx`** (real validation/crypto/lockout logic interleaved with their current hand-rolled modal markup) — these get their JSX/styling torn out and rebuilt 100% new exactly like every other file, with only the underlying logic (function bodies, store/crypto calls) lifted across unchanged, since that's the part under the hard "don't touch business logic" constraint.

Scope: their **mount point in `_layout.tsx` and their context-reading logic are untouched** (Phase 3 forbids changing `_layout.tsx` control flow); they are rebuilt only insofar as the modal they render is rebuilt onto `Sheet`/`Dialog`. Assigned to Phase 4, alongside their underlying modals.

**Dead code removed (no rebuild — deletion only):**

**Untouched (business/data/security logic — verified pure, no UI coupling):**

- `src/security/crypto.ts`, `src/services/storage.ts`, `src/services/backupService.ts`/`backup.ts`

- All 7 existing test files under `__tests__/` — a regression safety net; none should need edits, since no business logic moves. A test failure during this work signals scope creep, not an expected side effect.

**Two narrowly-scoped exceptions inside otherwise-untouched files** (referenced by §8's acceptance criteria; stated here so that reference resolves):
1. **`src/store/vaultStore.ts` contains 3 embedded `Alert.alert` calls** — presentation code living inside a store. They are **left exactly as they are**: not restyled, not migrated to `Snackbar`, not extracted. Touching them would mean editing a business-logic file for a purely cosmetic reason, which this plan forbids. The `Snackbar` migration in §3/§5 applies *only* to `Alert.alert` calls in screen and component files.
2. **`settingsStore.ts`'s UI-preference fields** (`themeMode`, `disguiseMode`, `viewMode`) are read and written by the redesigned screens through the **same `updateSetting` calls as today** — no signature, shape, or persistence change. The store file itself is not edited.

**How functionality stays connected:** every screen keeps calling the exact same store hooks, handler functions, and props into the logic-bearing components (`AccessKeyUnlockModal`, `AccessKeyRegistrationModal`, `AccessKeyScreenAuthModal`, `FolderPicker`/`MoveVaultModal`, `ClipboardBar`, `DestructiveConfirmModal`'s `useConfirmDestructive` hook). Only the JSX/styling wiring inside each file changes. `useTheme()`'s returned shape (`colors, isDark, themeMode, toggleTheme, space, screenPadding, headerPaddingTop, bottomTabSpacing, isTablet/isPhone/isSmallPhone, font, clampSize, responsiveSize, gridColumns, gridItemWidth, radius, shadow, …`) is frozen across this whole effort so no consumer needs a signature change.

**Calculator-disguise exemption (hard constraint):** `src/app/(auth)/login.tsx`'s `isCalc` branch (active when `disguiseMode === 'calculator'`) renders a convincing, un-themed iOS-style calculator by design — `lock.tsx` explicitly suppresses even a "Vault Locked" banner in this mode so a snooper sees nothing but an ordinary calculator. This branch gets **zero visual changes**. `Palette.calculator` in `Colors.ts` is confirmed dead code today (the calculator's colors are hardcoded `CALC_*` constants in `login.tsx`, not theme-driven) — it stays defined for type completeness but is explicitly commented as "do not wire up" so a future edit doesn't accidentally theme the disguise.

**Vestigial disguise skins:** `DisguiseMode` supports `'notes'` and `'utility'` (full alternate palette skins, resolved in `ThemeContext.tsx`) but neither has a Settings entry point today — no UI ever sets `disguiseMode` to those values. This is pre-existing and out of scope to add UI for (would be a new feature); the palettes are kept correct/complete but no new picker is built.

## 2. New Information Architecture

No route changes. Same two route groups, same 5-tab bottom navigation, same push/back model (`Slot`-based, no React Navigation Stack — confirmed zero `Stack.Screen`/`Tabs.` usage anywhere in the app today, and none is introduced).

- **Primary navigation:** `AnimatedTabBar` — Dashboard (home) ⇄ Favorites ⇄ Search (center raised button) ⇄ Trash ⇄ Settings, all via `router.push`. Tab set and order unchanged.
- **Secondary/contextual navigation:** two header types, kept distinct because they carry different navigational meaning:
  - `TabRootHeader` — **a net-new component** (does not exist at `0f05a73` — see the Phase 0 warning in Context), authored in Phase 3 and adopted by the 5 tab-root screens, each of which currently hand-rolls its own inline header (title + optional tagline + right-slot, no back button).
  - `VaultHeader` — exists today, hosted by **5 files** (`settings/customization`, `settings/storage`, `viewer/document`, `viewer/image`, `viewer/video`); back button → `router.back()`, title, right action slots. Gets a safe-area ownership fix (§5, "Header components") so it stops double-counting the top inset alongside `headerPaddingTop`. Two further screens — `settings/access-keys` and `settings/auth-key` — currently hand-roll inline headers with `headerPaddingTop` and **adopt `VaultHeader` for the first time** during their Phase 4 rewrite, bringing its host count to 7.
- **Modals/bottom-sheets:** consolidated onto two shapes used consistently everywhere — a centered `Dialog` (confirmations, short forms) and a bottom-anchored `Sheet` (action menus, longer pickers). Every current modal already fits one of these two shapes; this is a naming/consolidation decision, not new capability.
- **One navigational fix (presentation-only):** `src/app/(main)/settings/customization.tsx` (theme + grid-density picker) exists and works today but has **no entry point** from the Settings hub (`settings/index.tsx`) — confirmed zero `router.push('/(main)/settings/customization')` calls anywhere. A link card is added to the hub's "Visual Configurations" section pointing at it. This surfaces an existing screen through better structure, per the app's own "preserve existing features, present them better" directive — it adds no new screen, route, or capability.

User journeys are unchanged: cold start → onboarding → register → dashboard; returning-authenticated → dashboard; locked/backgrounded-too-long → lock screen (PIN or calculator disguise) → dashboard; dashboard/favorites/search → folder → viewer, with an optional access-key unlock gate wherever a folder/file is protected; settings hub → access-keys / auth-key / customization / storage, each still gated exactly as today (access-keys and auth-key sub-screens keep their PIN re-verification gates).

## 3. Screen-by-Screen Redesign

For every screen, primary/secondary actions, data hierarchy, and state handling are unchanged in *substance* — only layout, component choice, and visual treatment change. "New primitive" references are defined in §5.

Three state categories apply uniformly rather than needing a per-screen callout: **offline** is not applicable anywhere in this app — it is 100% local/on-device with zero network dependency, so there is no offline/online distinction to design for. **Success** states split by weight, per Material's own distinction between low- and high-emphasis feedback: a simple one-off confirmation with nothing further for the user to decide (today's `Alert.alert('Paste Complete', …)`, `'Access Key Assigned'`, `'Export Complete'`, and similar single-OK-button alerts scattered across dashboard/favorites/search/folder) becomes the new `Snackbar` primitive (§5) — a transient, non-blocking bottom toast, which is the Material-correct affordance for this and doesn't exist in the app today; anything carrying real content or a further choice (the backup-result screen with its Retry action, the restore-passphrase prompt) stays a `Dialog`. This is a deliberate, Material-driven addition to the design system, not scope creep — the underlying action (the paste, the export, the key assignment) succeeds or fails exactly as it does today; only how that outcome is surfaced changes, and only for outcomes that were already non-blocking, single-button acknowledgments. **Disabled** states are handled centrally by the new `Button`/`TextField` primitives, which expose a `disabled` prop driven by the same validation/in-flight checks each screen already performs (e.g. a submit button disables itself while its matching store action is pending) — so disabled state is a primitive-level guarantee, not something each screen table row needs to restate.

## 4. Design System

**Direction:** a clean break from the current violet-indigo-on-warm-cream look, not a refinement of it. The old palette is discarded wholesale and replaced with a new identity built for what this app actually is — a security vault, not a consumer fintech app: a cool, confident **"Vault Blue"** system — deep sapphire `primary` (`#1D4ED8`) against cool neutral surfaces (light: `#F3F5F8`, a crisp near-white slate, not cream; dark: near-black slate `#0B0F14`) with a **teal-emerald `secondary`** (`#0E9F6E`) reserved for verified/secure/success signaling — a color the old palette never used, so "this item is protected" reads as a distinct, deliberate highlight rather than a shade of the same primary. Exact hex values are validated for WCAG contrast in Phase 1 (§7) and may shift slightly during that pass, but the hue family and neutral-cool direction is the decision, not a placeholder.

**The Material × Flat hybrid, made concrete (not just named):** the two systems are not blended by softening one against the other — they're cleanly divided by what each governs, and every rule below in §4/§5 is traceable to one side of this split:
- **Material 3 owns structure and behavior:** the component vocabulary (`Card`, `Dialog`, `Sheet`/bottom sheet, `Snackbar`, `Chip`, `SwitchRow`, `SegmentedControl`, FAB — all named explicitly in §5, matching Material's own component list), elevation as the *sole* mechanism for signaling hierarchy (never a border-only or color-only cue for "this is raised above that"), Material 3's "state layer" technique for interaction feedback (an 8–12% black/white overlay tint over the base surface for hover/focus/pressed, not a swap to a different hardcoded color), and platform-adaptive touch feedback — `Pressable` with `android_ripple` (Material's signature ripple, Android-only per Material's own guidance) and a scale/opacity press state on iOS.
- **Flat design owns rendering weight:** every one of those Material surfaces is drawn with solid fills, no gradients, no skeuomorphic gloss or texture (`expo-linear-gradient` is not installed and is not added), minimal ornamentation, and shadows kept genuinely subtle (`sm`/`md` for most surfaces, `lg`/`xl` reserved for the handful of things — dialogs, sheets, the FAB — that are actually meant to float above everything else, per the "Elevation" rule below) — paired with a permanent hairline border rather than a heavier shadow wherever a surface needs to read as separated on a background where shadow alone is too weak (notably `amoled`'s true-black surfaces).
- In short: a `Card` behaves and animates like Material (elevation, state layers, ripple) but is drawn flat (solid fill, thin border, no gloss). That pairing — not a compromise between the two — is what "hybrid" means throughout this plan.

**Color tokens** (`src/constants/Colors.ts`) — `ThemeColors` v2 makes every field mandatory (no more `dashboardX?`/`fabX?` optionals, no more `?? colors.X` fallback chains — **133 of them across 12 files**, concentrated in `MoveVaultModal` (31), `AccessKeyUnlockModal` (24), and `RenameModal` (13)):
`background, surface, surfaceHover, surfaceElevated, navBar, text, textSecondary, textMuted, primary, primaryLight, primaryDark, onPrimary (new — replaces hardcoded '#FFFFFF' at 30+ sites), secondary (new — the teal-emerald `#0E9F6E` described above; a real Material second color role, not just an "accent" that happens to double as the success tint), border, borderLight, error, warning, success, info (new — a neutral slate-blue tone for informational banners/notices, e.g. the restore-passphrase explanation, distinct from both `primary` and `error`/`warning`/`success`), shadow, glass, fabBg, fabText`, plus the existing fully-populated `vault*` namespace (repointed to the new hues, not kept at their current values). `accent` is retired as a field name in favor of `secondary` — same color, a name that actually matches its Material role and satisfies this app's own required token list (`primary, secondary, surface, background, success, warning, error, information`). `backgroundGradientStart/End` (dead — consumed nowhere) is removed outright, since nothing reads it. Every *other* retired field name (`dashboardBg`, `dashboardSurface`, `dashboardSurfaceHover`, `dashboardAccent`, `dashboardText`, `dashboardTextMuted`, `dashboardBorder`, `dashboardNavBar`, `accent`) is kept in `ThemeColors` as a thin deprecated alias — pointing at its new-name replacement's value — through Phases 1–3 and however much of Phase 4 hasn't yet migrated its last consumer, precisely mirroring the "old file deleted the instant its last caller migrates" rule already applied to `AnimatedActionSheet`/`StyledButton`/`AnimatedCard` in §7. This is what actually makes Phase 1's "every existing consumer keeps compiling" claim true — without the aliases, Phase 1 would break every not-yet-migrated screen's `colors.dashboardBg`/`colors.accent` references immediately, long before Phase 4 gets to them. All six palettes (`light, dark, amoled, calculator [kept inert, documented — see §1], notes, utility`) are redrawn around the new primary/secondary/neutral direction and populate every field — TypeScript enforces the "every field populated" part, which is what actually fixes the "only 2 of 6 palettes have dashboard tokens" bug; the color values themselves are a deliberate new design, not a mechanical carry-forward of the old ones.

**Light/dark/disguise strategy:** `themeMode: 'light'|'dark'|'amoled'` picks the base palette; `disguiseMode: 'notes'|'utility'` fully overrides it for the decoy-skin feature (unchanged mechanism, just cleaner tokens); `disguiseMode: 'calculator'` bypasses theming entirely inside `login.tsx` by design (§1).

**Typography** — new `src/constants/typography.ts`, a named scale (`display 32/800, title 24/800, headline 19/800, subtitle 16/700, body 14/500, label 13/600, caption 12/600, eyebrow 11/700 uppercase`) layered on the existing `font()` responsive helper — replaces today's scattered magic-number font sizes with one source of truth. `font()`'s signature and dynamic-type clamp behavior (`getFontScale`, 0.875–1.25×) are untouched.

**Spacing/grid** — `src/utils/responsive.ts`'s existing 0–64/4px spacing scale and `xs/sm/md/lg/xl` breakpoints are kept as-is (already well-designed); its dead duplicate `radius` export (byte-identical to `constants/radius.ts`, imported nowhere) is deleted to remove a double-source-of-truth risk. `isTablet`/`isPhone`/`isSmallPhone` breakpoint detection unchanged.

**Iconography** — 100% `lucide-react-native` (already fully consistent app-wide), no second icon set introduced. Explicit size/stroke rules by context: inline/metadata 12–14px, buttons 18–20px, list/header icons 20–24px, category/vault chips 22–28px (via `responsiveSize`), empty-state illustrations 32–48px; stroke 2 at rest, +0.3–0.5 when active/selected (matches the existing `AnimatedTabBar` convention).

It is **authored in Phase 1** as a new export from `src/utils/responsive.ts`, and becomes a mandatory floor on every new interactive primitive.

**Buttons and action hierarchy** — new `Button` primitive: variants `primary/secondary/tertiary/danger/ghost`, sizes `sm/md/lg`, `loading`/`disabled` states built in (replaces the ad hoc opacity+text-swap pattern duplicated across `auth-key.tsx`/`access-keys.tsx`/`register.tsx`), `MIN_TOUCH_TARGET` non-optional. `StyledButton` is retired (fully replaced, not kept alongside).

**Form controls** — `TextField` (label/error/helper/secure-toggle, replacing 6 duplicated eye-icon blocks), `SwitchRow` (label+description+icon+switch row, generalized from the current `settings/index.tsx`-local `SettingCard`), `SegmentedControl` (replaces `customization.tsx`'s local radio-row pattern).

**Cards, lists, chips, badges, alerts, dialogs, sheets, snackbars, loading** — see §5 (Component Architecture) for the concrete primitive list. All but one of these consolidate an existing hand-rolled equivalent identified in the audit; the exception is `Snackbar`, added specifically to complete Material's component vocabulary where the current app has no non-blocking feedback mechanism at all (every confirmation today is a blocking `Alert.alert`) — see §3's success-state rule for exactly which confirmations move to it.

**Interaction states** — every new primitive defines default/pressed/focused/selected/disabled/loading states explicitly (most current components today only vary opacity on press and have no defined focus/loading state); success/error states use icon+color+text together, never color alone (§6).

## 5. Component Architecture

New directory `src/components/primitives/`, consolidating **~24 distinct hand-rolled modal call sites**: 8 named components (`RenameModal`, `DestructiveConfirmModal`, `FolderPicker`, `MoveVaultModal`, `BackupConfirmDialog`, `AccessKeyRegistrationModal`, `AccessKeyUnlockModal`, `AccessKeyScreenAuthModal`) plus **16 inline `<Modal>` blocks across 6 screen files** — `folder/[id].tsx` (4), `settings/index.tsx` (4), `favorites.tsx` (3), `dashboard.tsx` (2), `search.tsx` (2), `trash.tsx` (1). An earlier draft put this at "15 sites / 7 inline blocks across 3 files", omitting `favorites`, `search`, and `trash` entirely; **size Phase 2 and Phase 4 against the corrected figure**, since the three omitted files carry 6 of the 16 inline blocks:

An earlier draft claimed `dashboard.tsx`, `folder/[id].tsx`, `favorites.tsx`, `search.tsx`, and `trash.tsx` were also callers — none of them import it; they use inline `<Modal>` blocks.) **Header components — two purpose-built types, both getting entirely new visuals:** `TabRootHeader` and `VaultHeader` stay as two distinct components — not for continuity, but because they carry different navigational meaning (tab-root vs. pushed-detail) that a single merged header would blur. Both get fully new layouts/styling per §3, and — because each is shared chrome consumed by 5–8 screens rather than something local to one screen — both are rebuilt once, up front in Phase 3 (§7), before Phase 4 touches any of their consuming screens; the one thing genuinely reused across the rewrite is a bug fix. `VaultHeader.tsx` currently applies a hardcoded `headerPaddingTop` constant (`ThemeContext.tsx`) *inside* a plain `View`, while each of its host screens wraps it in a default-all-edges `SafeAreaView` — so the real top safe-area inset and the hardcoded padding both apply, stacking to an oversized gap. **The fix is not mechanical, and the earlier "8 host screens, just change the `edges` prop" description was wrong on both counts:**

- **There are 5 host files, not 8:** `settings/customization`, `settings/storage`, `viewer/document`, `viewer/image`, `viewer/video`. (`settings/access-keys` and `settings/auth-key` hand-roll inline headers and only adopt `VaultHeader` later, in Phase 4 — see §2.)
- **Three of the five import `SafeAreaView` from `react-native`, not `react-native-safe-area-context`:** `viewer/document`, `viewer/image`, `viewer/video`. React Native's own `SafeAreaView` **has no `edges` prop at all** — setting one is a silent no-op — and it is **iOS-only**, a plain `View` on Android. So on those three screens the bug does not reproduce on Android, and the fix requires **first migrating the import to `react-native-safe-area-context`**, then setting `edges`. Treat this as a real code change per viewer, not a prop tweak.
- Only `settings/customization` and `settings/storage` already use the context-aware `SafeAreaView` and are a genuine one-line `edges` change.

Fix, then: give `VaultHeader` a self-owned top safe area (`useSafeAreaInsets()` internally, replacing `headerPaddingTop`) — a pattern that must be **written fresh**, since the `TabRootHeader` it was said to copy does not exist at baseline (see Context) — migrate the three viewers' `SafeAreaView` import, and set `edges={['bottom','left','right']}` on all five hosts. Author `TabRootHeader` on the same self-owned-inset pattern so the two headers agree. `ViewModeMenu.tsx` — the grid/list picker rendered in the right-slot of 5 screens' headers (`dashboard`, `favorites`, `search`, `trash`, `folder/[id]` — notably absent from `settings/index`, which has no right-slot control), and itself a small store-reading/writing component (`useSettingsStore().viewMode`) — gets the same up-front Phase 3 treatment: new trigger visual, and its internal sheet migrated onto the `Sheet`/`Dialog` primitives from §5 rather than a direct `AnimatedActionSheet` call.

**Business-logic components — 100% new visuals, logic lifted across unchanged:** `AccessKeyPicker`, `AccessKeyRegistrationModal`, `AccessKeyScreenAuthModal`, `AccessKeyUnlockModal`, `FolderPicker`, `MoveVaultModal`, `RenameModal`, `ClipboardBar`, `AnimatedTabBar` get the same full JSX/StyleSheet teardown as every other component; what carries over is narrowly the prop interface, handler function bodies, and store calls (e.g. `SecureCrypto.secureCompare`, `useLockoutStore` checks) — the actual security/data behavior — never a single line of the old markup or style. `AnimatedTabBar`'s one real bug fix along the way: its central Search button currently hardcodes `#5162FF` regardless of theme/disguise skin — routed through `colors.primary`/`colors.fabBg` instead.

**Split seam (utility, not component):** `src/utils/getFileType.tsx` currently fuses file-type classification with hardcoded icon JSX. Split into a pure classifier (returns a type tag) + the new design system owning the icon/color mapping centrally — this also resolves `trash.tsx`'s separate inline duplicate of the same classification logic (`trash.tsx:116-137`). Note the file's colors come from **`CategoryTint`, a standalone export of `Colors.ts` that is not a member of `ThemeColors`** and so is invisible to the "every palette populates every field" TypeScript check; it must be deliberately redrawn to the new palette in Phase 1 (§1) or the file-category icons will keep their old hues while everything around them changes.

## 6. Accessibility Requirements

- **Contrast:** the new `primary` (`#1D4ED8`), the new `secondary` (`#0E9F6E`), and all text/background pairings across all 6 redrawn palettes are checked against WCAG AA (4.5:1 body, 3:1 large text) once, centrally, during token authoring (§7 Phase 1) — not left to per-screen judgment.
- **Touch targets:** `MIN_TOUCH_TARGET` (44) — **newly authored in Phase 1, not pre-existing (§4)** — becomes a hard floor baked into `Button`/`Chip`/icon-button primitives (via `hitSlop` where the visual size is smaller), not an opt-in convention. Phase 5 includes a grep-audit of any remaining bespoke `TouchableOpacity` for compliance.
- **Text scaling:** unchanged mechanism — `getFontScale()` (clamped 0.875–1.25×) — the new `Type` typography scale is defined in base points and always routed through `font()`, so nothing bypasses the existing clamp.
- **Screen-reader labels / semantic structure:** every new primitive sets `accessibilityRole`/`accessibilityLabel`/`accessibilityState` by default (e.g. `Button` always sets role="button" + `disabled`/`busy` state) so screens can't forget it — unlike today's per-`TouchableOpacity` opt-in pattern (several icon-only buttons, e.g. `folder/[id].tsx`'s overflow menus, currently have no label at all).
- **Keyboard navigation and focus indicators:** all interactive primitives remain real `Pressable`/`TouchableOpacity`-based elements, never `View`+`onTouchStart` fakes, so platform focus/TalkBack/VoiceOver traversal works correctly on mobile with no custom keyboard-nav code needed. Separately, every primitive shows a visible focus ring (a themed outline using `secondary`, driven by `onFocus`/`onBlur`) when reached via an external keyboard, D-pad, or switch-access device — today's app has no such indicator on any control, since touch is the only input path it was built for.
- **Reduced motion:** one shared check via `AccessibilityInfo.isReduceMotionEnabled()` inside the new `useScreenEnterAnimation()` hook and inside `Dialog`/`Sheet`'s enter/exit — when true, animation durations collapse to `Durations.instant` (already `0`). One code path, not a per-screen retrofit.
- **Color is never the only signal:** lock/favorite/encrypted badges already pair icon+color (kept); the one gap — category filter pills distinguishing active/inactive partly by color/border alone — is fixed in the new `Chip` primitive by also changing label weight and adding a checkmark-style active indicator.
- **Error messaging:** every form control (`TextField`, PIN entry, password strength) surfaces errors as icon+text, never a bare red border.

## Verification

Since this is a UI-only change to an Expo/React Native app with no test coverage on the presentation layer (all 7 existing tests target business logic and must keep passing untouched), verification is primarily manual + automated-logic-regression:

1. **Automated regression:** run `npm test` (jest via `jest-expo`) after each phase — all 7 suites (`store/__tests__`, `services/__tests__`, `security/__tests__`, `utils/__tests__/calculatorExpression.test.ts`) must stay green with zero edits.
